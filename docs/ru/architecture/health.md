# TLS/SNI-проверки relay

Проверка соединяется с числовым IPv4 кандидата на TCP 443. Домен сервиса передаётся как server_hostname при TLS handshake. Системное разрешение имени сервиса не используется для выбора адреса соединения.

Контекст создаётся через ssl.create_default_context. Проверка цепочки сертификата и hostname обязательна: insecure context отклоняется до соединения. Неверный или просроченный сертификат не даёт tls_ok. Успешного TCP-соединения недостаточно.

## Ограничения

Одна попытка имеет общий deadline до 4 секунд для TCP connect и TLS handshake. После connect сокету назначается только оставшаяся часть timeout. Одна проверка кандидата содержит до двух попыток. Одновременно выполняется не больше восьми проб; первоначальный batch включает до двух кандидатов на домен. Общий бюджет — до 200 проверок пар домен/IP за запуск, включая отложенные повторные проверки. Лимиты проверяются при выборе batch и перед его выполнением.

Ожидаемые сетевые и TLS-ошибки дают failed. Неожиданное исключение даёт unknown без раскрытия внутреннего текста ошибки. Сокеты закрываются и при неудаче.

## Выбор кандидатов для проверки

Текущий выбранный маршрут проверяется первым. Остальные кандидаты упорядочены по provider_order сервиса, priority и числовому IPv4. IPv6 остаётся в metadata источника и не участвует в IPv4-пробах.

Сохранённый ProbeCursor задаёт начальную позицию в полном упорядоченном пуле. Если все проверенные кандидаты домена failed/unknown, advance_probe_cursors перемещает курсор за последнего проверенного кандидата. Следующий запуск проверит следующие адреса вместо постоянного повторения первых двух. Функция возвращает новые курсоры; контроллер сохраняет их вместе с наблюдениями при разрешённом `sync --apply`, в том числе для продвижения неудачного batch. Read-only preview и doctor курсоры не сохраняют.

Результаты batch сохраняют порядок входных кандидатов независимо от порядка завершения потоков. При max_candidates_per_domain=1 текущий маршрут занимает единственное место; для проверки резервного адреса вместе с текущим требуется значение 2.

## Повторная проверка временного сбоя

Если текущий опубликованный адрес не ответил из-за сетевого таймаута или ошибки соединения, контроллер ждёт 5 секунд и один раз повторно проверяет этот адрес. Повтор выполняется до построения итогового плана и любой записи DNS или состояния. Он применяется к текущим маршрутам с неизменной политикой, которые иначе были бы заменены резервным адресом либо остались бы неподтверждёнными. Здоровые адреса, новые кандидаты и ошибки сертификатов не получают дополнительного повтора.

На повтор выделяется только остаток общего бюджета `max_pairs`: когда он исчерпан, контроллер использует первоначальные результаты и обычные проверки безопасности. В одной повторной проверке также действует `probe.attempts`, поэтому текущий адрес может получить до четырёх TCP/TLS-попыток за запуск. Пауза выполняется один раз на весь повторный batch. Offline-просмотр не запускает повтор.

Успешный повтор подтверждает текущий маршрут и позволяет сохранить его. Неопределённый результат не считается успешным. Для каждого повторно проверенного адреса routing использует последний результат; исходная неудачная проба не добавляется рядом с ним как противоречивое наблюдение. Проверки DNS, порог 85%, обязательные домены и лимиты изменений остаются прежними. API-записи, recovery и rollback этим механизмом не повторяются.

## Значение результата

- tls_ok — выполнен TLS handshake через конкретный IP с проверкой сертификата нужного домена.
- failed — ограниченные попытки не подтвердили TLS-связь.
- unknown — проверка не смогла надёжно определить состояние.

tls_ok не подтверждает вход в аккаунт, обработку сообщения, загрузку файлов, отсутствие WAF или разрешённую страну выхода. Проверка не передаёт cookies, логины и прикладные HTTP-запросы.

vantage указывает место выполнения контроллера: local или github_runner. latency_ms — время успешной TCP/TLS-попытки с этой точки, а не задержка пользователя из другой сети. Неуспешным пробам не приписывается успешная latency.

## Пределы приёмки

TLS/SNI-проверки входят в текущий контроллер: их результаты передаются в [routing](routing.md), а DNS-изменения применяются отдельным [reconcile](reconcile.md) после проверок безопасности. Успешный TLS не подтверждает DNS-публикацию или прикладной сценарий.

Порог доступности маршрутов — не менее 85% доменов каждого включённого сервиса при подтверждении всех required domains. `doctor` без `--apply` проверяет источники, TLS и профильные DNS-ответы без изменения DNS и ledger. Результаты приёмки, включая отдельную проверку устройства, описаны в [матрице приёмки](../project/acceptance.md).
