# GitHub Actions

В репозитории два workflow: `CI` проверяет код без credentials; `SmartGate sync` выполняет контроллер на default branch. Автоматическое применение по умолчанию выключено. При `SMARTGATE_APPLY_ENABLED=false` запуск по расписанию выполняет `doctor`: проверяет текущие DNS-ответы и доступность маршрутов, не меняя DNS-записи или состояние. При `true` расписание выполняет `sync --apply`.

## Подготовка

Сначала создайте свою копию репозитория: **Fork → Copy the main branch only**. Не копируйте чужую ветку состояния. В своей копии откройте **Actions** и включите workflows, если они отключены. Для приватной установки используйте отдельную приватную копию исходников.

Выберите [DNS-адаптер](../providers/dns/README.md) и подготовьте отдельное назначение по его руководству. Начальная конфигурация использует один рабочий адаптер; self-hosted reference-адаптеры доступны для просмотра, но не для production apply.

В **Settings → Environments** создайте Environment `smartgate`. Подготовьте [ключ состояния и его backup](privacy.md#подготовьте-ключ). Добавьте параметры выбранного провайдера и ключ шифрования:

| Тип | Имя | Когда требуется |
| --- | --- | --- |
| Secret | `SMARTGATE_STATE_ENCRYPTION_KEY` | Для live Git state: 32 случайных байта в Base64 |
| Secret | `SMARTGATE_DNS_API_KEY` | API key или Bearer token |
| Secret | `SMARTGATE_DNS_USERNAME` | Basic authentication |
| Secret | `SMARTGATE_DNS_PASSWORD` | Basic authentication |
| Secret | `SMARTGATE_DNS_PROFILE_ID` | Профиль адаптера, которому нужен profile ID |
| Secret | `SMARTGATE_DNS_API_URL` | HTTPS origin собственного API |
| Secret | `SMARTGATE_DNS_NAMESPACE` | Выделенный scope или существующая zone собственного DNS |
| Secret | `SMARTGATE_DNS_DOH_URL` | HTTPS DoH собственного DNS |
| Variable | `SMARTGATE_APPLY_ENABLED` | `false` до ручной приёмки |

Обновите DNS-блок `config/smartgate.actions.toml` по [примеру выбранного адаптера](../../../config/dns). Сохраняйте state provider `git_branch`, branch `smartgate-state` и каталог сервисов. Сервер с непроверенными capabilities остаётся read-only независимо от `sync.enabled` и workflow input.

DNS-идентификаторы и адреса API/DoH тоже храните в **Secrets**: GitHub маскирует их в служебном env выводе до старта контроллера. Прежние Variables остаются fallback для совместимости, но их значения могут попасть в логи. При переносе в Secret сохраняйте то же значение; DNS-назначение не меняется. Совпадающие старые aliases временно допустимы, конфликт значений блокирует запуск.

`GITHUB_TOKEN` выдаётся самим Actions. Не добавляйте его как свой secret. Ограничьте Environment default branch и при необходимости настройте required reviewers.

Конфигурация workflow — `config/smartgate.actions.toml`; `sync.enabled=true` разрешает подтверждённый ручной apply; автоматические записи дополнительно требуют `SMARTGATE_APPLY_ENABLED=true`. State хранится через GitBranchStateStore в отдельной orphan-ветке `smartgate-state`. Отсутствующая ветка не создаётся просмотром; её может инициализировать только явный bootstrap.

Не подключайте устройство к этому DNS-назначению до проверки результата и готовности relay. CLI не меняет DNS компьютера.

## Ручные запуски

Откройте Actions → SmartGate sync → Run workflow на default branch. Начните с `command=preview`, `apply=false`, `bootstrap=false`. Посмотрите Summary с агрегатами. Для проверки доменов и плана скачайте `report.enc.json` и [расшифруйте локально](privacy.md#чтение-подробного-отчёта).

Для первого применения:

1. Проверьте пустое DNS-назначение, домены и изменения в preview.
2. Проверьте `sync.enabled=true` в `config/smartgate.actions.toml` на default branch. Эта конфигурация разрешает явно подтверждённый ручной apply; variable расписания оставьте `false`.
3. Если число операций превышает `max_mutations=20`, после просмотра плана временно измените этот предел в `config/smartgate.actions.toml` на default branch своей копии. Например, для 25 create достаточно 30. Повторите preview, разберите остальные причины блокировки и только затем запустите `command=sync`, `apply=true`, `bootstrap=true`. Bootstrap не отменяет лимит количества операций. После первого применения верните обычный предел 20.
4. Для повторной приёмки выберите `command=sync`, `apply=true`, `bootstrap=false`, **`require_no_change=true`**. Ожидаемый результат — no_change при здоровых маршрутах и совпадающих DNS. Если свежий план содержит хотя бы одну операцию, запуск завершится blocked без изменений DNS или состояния.

### Проверка без изменений DNS

`require_no_change=true` доступен только для ручного `sync` с `apply=true` без bootstrap. Контроллер проверяет план внутри самого запуска: даже нулевой preview не гарантирует, что источники и маршруты останутся прежними к следующему sync. Любые create, replace или delete блокируются до preflight и записей. Незавершённый журнал также блокирует проверку; автоматическое recovery не запускается.

При нулевом плане выполняются обычные проверки API и DNS. Контроллер может обновить наблюдения и метаданные маршрутов в ветке состояния; DNS-записи он не меняет. Ошибки проверок и порог доступности 85% сохраняют прежнее значение. Обычное расписание использует `require_no_change=false`.

Если проверка заблокирована, изучите новый план и отдельно разрешите необходимые изменения; для их применения нужен обычный ручной sync. Не выключайте защиту только ради зелёного статуса.

Ручной `apply=true` разрешает запись независимо от variable автоматического расписания. Поэтому `SMARTGATE_APPLY_ENABLED=false` можно оставить на всё время ручной приёмки. Для recover/rollback применяется такое же явное ручное разрешение; конфигурация должна позволять sync.

Topic/state branches не исполняют secret-bearing sync job. Workflow должен присутствовать на default branch; отправка рабочей ветки сама по себе расписание не включает.

## Обновление legacy ledger

Для существующей установки новая схема DNS-конфигурации требует явного перехода состояния. Остановите автоматическое применение и дождитесь завершения активных/ожидающих writers перед сменой workflow concurrency. Сохраните старые настройки, проверьте API records и ledger, затем создайте нейтральные Secrets/Variables. Workflow временно принимает прежние имена только для миграции действующего адаптера; конфликт старого и нового значения блокирует запуск.

На default branch выполните `command=state-upgrade`, `apply=false`, `bootstrap=false`; после проверки — тот же command с `apply=true`. Новый файл и удаление старого пути сохраняются одной CAS-операцией. DNS-записи эта команда не меняет. Незавершённый журнал сначала восстановите прежней конфигурацией. Подробности — [формат и upgrade](state.md#обновление-старого-состояния).

После read-back повторите doctor и новый preview. Рабочий sync разрешён только после проверки свежего плана. Удаление прежних Secrets и восстановление расписания выполняются после подтверждения перехода. Upgrade нельзя запускать по schedule или вместе с bootstrap.

## Расписание и остановка

Cron `17 */6 * * *` запускает контроллер в 00:17, 06:17, 12:17 и 18:17 UTC. При `SMARTGATE_APPLY_ENABLED=false` выполняется read-only `doctor` с проверкой DNS управляемых записей. До первого успешного bootstrap он не подтверждает готовность и может завершаться `degraded`: расписание не инициализирует отсутствующее состояние. После проверки ручного apply, повторного no-op, профильных DNS-ответов и сценария приложения можно установить variable в `true`. `sync.enabled=true` также обязателен.

Чтобы остановить автоматические записи, верните variable в `false`. Для блокировки DNS apply установите `sync.enabled=false`. Команда state-upgrade отдельно требует явного ручного разрешения и меняет только состояние. Для полной остановки чтений и probes отключите workflow в Actions.

GitHub запускает schedule на default branch; запуск может задерживаться или быть пропущен. В публичном репозитории расписание отключается после 60 дней без активности. Это не realtime failover и не SLA. Подробнее: [GitHub schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

Запуски используют общую concurrency group репозитория и `cancel-in-progress: false`; активный запуск не отменяется новым. CAS state и execution lease защищают от другого writer вне Actions. GitHub может заменить ожидающий запуск более новым: [правила concurrency](https://docs.github.com/en/actions/concepts/workflows-and-actions/concurrency).

## State, отчёты и права

Sync job получает `contents: write` для сохранения state; CI — только read. GitHub permission не ограничивается одной веткой: ограничение state branch обеспечивается адаптером и политикой workflow. Не используйте `pull_request_target` и не запускайте этот job с кодом fork PR.

**Ветка состояния в public доступна читателям, но её содержимое зашифровано.** Подробности маршрутов доступны с ключом; конфигурация, размеры и время коммитов остаются видимыми. Перед публикацией проверьте старую plaintext историю и прежние Actions outputs. [Приватность](privacy.md).

Summary содержит агрегаты. Artifact включает безопасные `report.json`, `report.md` и зашифрованный `report.enc.json`. Artifact хранится 7 дней; state, `.env`, credentials и raw evidence в него не входят. При ошибке до запуска CLI создаётся резервный отчёт. После жёсткого timeout/cancellation загрузка отчёта может не завершиться: смотрите durable state и workflow logs.

Timeout job — 25 минут, execution lease контроллера — 20 минут. Перед recovery убедитесь, что прежний процесс завершён; Actions не выполняет досрочный takeover автоматически.

## Статусы Deployment

> [!NOTE]
> Job с Environment `smartgate` создаёт связанный Deployment в GitHub. Это запись о выполнении контроллера; отдельный веб-сайт здесь не развёртывается.

CLI сохраняет код **3** для `degraded`. Actions дополнительно различает успешную синхронизацию с предупреждениями: если обязательные маршруты доступны, применение завершено, журнал `verified`, все DNS-проверки успешны и отсутствуют ошибки, недоступные необязательные маршруты дают зелёный workflow с warning в Summary только при доступности минимум **85% доменов каждого включённого сервиса**. Отчёт сохраняет `status=degraded`, `exit_code=3` и показывает `workflow_exit_code=0`. После завершённого rollback статус журнала `rolled_back` также допускается, если новый sync имеет пустой план, явно подтверждает ноль изменений и проходит все остальные проверки. Это проверка текущего DNS без новых операций; статус прежнего журнала не переписывается.

Проверка `doctor` тоже может быть зелёной с необязательными предупреждениями: свежий план должен быть пустым, журнал завершённым, доступность каждого сервиса — не ниже 85%, а все текущие DNS-проверки — успешными. Контроллер повторно читает API и состояние после проверки; изменение любого снимка блокирует результат. Журнал не переписывается. Обычные `preview` и `sync` без apply по-прежнему не подтверждают успешную DNS-проверку.

При сетевом сбое текущего relay контроллер автоматически [повторяет TLS-проверку после паузы](../architecture/health.md#повторная-проверка-временного-сбоя). Это часть того же запуска по расписанию; отдельный ручной запуск не требуется для подтверждения кратковременного сбоя. Повтор не меняет правила успешного статуса и не повторяет DNS-записи.

Сбой источника/API, обязательного маршрута, проверок DNS, неопределённое применение и read-only preview с проблемами остаются красными. Старые failed runs не переписываются задним числом.

| Ситуация | Следующее действие |
| --- | --- |
| `verified`, DNS checks успешны, optional routes недоступны | Проверить доступность сервиса и предупреждения; существующие маршруты могут работать |
| `partial` или незавершённый журнал | Выполнить recovery по [runbook](runbook.md), исключив параллельный writer |
| `blocked` | Разобрать конфликт, лимиты или preconditions; применение не разрешено |

Не заменяйте любой ненулевой код успешным результатом: это скрывает реальные ошибки и неопределённые mutations.

## Неуспешный запуск и квоты

Сначала прочитайте status и exit code отчёта. Pending/partial требуют recovery, ownership conflict — разбора drift. Новый sync с apply сначала восстанавливает pending и заканчивает команду; следующий sync строит новый план. Уведомления о failed workflows настраиваются стандартными средствами GitHub; контроллер не рассылает сообщения.

Проверяйте квоты и ограничения выбранного DNS-провайдера по его [руководству](../providers/dns/README.md). DNS-проверки контроллера тоже учитываются сервисом.

DNS API transport ограничен 400 вызовами за запуск; изменения сериализованы. Конкретный адаптер может вводить дополнительные ограничения частоты. CI проверяет locked install и offline suite на Windows/Python 3.12 и Linux/Python 3.12/3.13. Ссылки Actions закреплены полными upstream commit SHA.

GitHub state transport также ограничен 400 вызовами. Перед записью проверяется бюджет всей партии; слишком большая партия блокируется до bootstrap и DNS-изменений. Кеш неизменяемых Git objects уменьшает число запросов, сохраняя свежие проверки branch ref и CAS; подробнее в [StateStore](state.md).


### Порог доступности маршрутов

Для каждого включённого сервиса считаются уникальные домены из текущих решений, сохранённых источников и управляемых записей, а также явно обязательные домены. Рабочим считается домен с выбранным или сохранённым подтверждённым маршрутом. Unknown, failed и сохранение маршрута с degraded не считаются успехом. Отключённые наборы исключены.

Порог **85%** проверяется по точным числам до округления: 17/20 проходят, 16/20 не проходят; 11/13 = 84,62% не проходят. Каждый сервис оценивается отдельно; при пересечении областей общий домен входит в каждый подходящий набор с учётом его исключений. Обязательные домены должны работать все; API, journal и опубликованные DNS-записи проходят полную проверку. Процент влияет на отображение успешного sync, а не разрешает небезопасное применение.

Summary и JSON содержат число рабочих доменов, общее число и процент. Это покрытие известных маршрутов, не гарантия всех функций приложения или всех возможных поддоменов. Потеря домена из нового источника не убирает его сразу из знаменателя, пока он известен сохранённому источнику/ownership. Полностью неизвестный сервис не получает зелёный результат.

## Шифрование существующего состояния

Ручной `state-encrypt` сначала выполняется с `apply=false`, затем после проверки с `apply=true`. Он не меняет DNS, не запускается по расписанию и несовместим с bootstrap, rollback ID и `require_no_change`. Новая версия требует ключ и отвергает plaintext обычными командами. ## Ручная смена ключа

`state-rotate` проверяет или перешифровывает один привязанный документ Git-состояния. Требуются выключенное автоприменение и временный Secret нового ключа. Перед CAS-записью создаётся зашифрованный backup; основной Secret заменяется вручную. [Полный порядок](key-rotation.md).

## Мониторинг маршрутов

Отдельный [короткий мониторинг](monitoring.md) может собирать DNS/TLS/HTTP-наблюдения раз в полчаса без изменения DNS и создания Deployments. Включайте переменную репозитория после успешной ручной проверки; учитывайте расход Actions.
