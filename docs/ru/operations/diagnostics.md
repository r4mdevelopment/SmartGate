# Причины сбоев в Summary

Summary показывает статус, число операций и DNS-проверок, а также таблицу **What happened**: безопасный код причины, объяснение и следующий шаг. Домены, IP, идентификаторы профилей и тексты ответов API остаются в зашифрованном отчёте.

| Код | Что произошло | Что делать |
| --- | --- | --- |
| `source_unavailable` | Не удалось получить или проверить источник адресов relay | Повторить preview; при повторении проверить источник в подробном отчёте |
| `required_route_unavailable` | Для обязательного домена нет пригодного проверенного маршрута | Запустить doctor и проверить сервис на устройстве; не обходить проблему повышением лимитов |
| `availability_below_threshold` | Доступность маршрутов сервиса ниже 85% | Посмотреть результаты doctor и подробности маршрутов |
| `dns_api_unavailable` | Запрос к API DNS-провайдера не завершён | Проверить состояние провайдера и ключи; перед apply проверить pending journal |
| `dns_verification_failed` | DNS-ответы не прошли ожидаемые проверки | Повторить doctor после небольшой паузы; для pending journal следовать recovery |
| `verification_incomplete` | Doctor не смог подтвердить всю сохранённую конфигурацию | Сверить preview и journal с инструкцией первого запуска или восстановления |
| `state_conflict` | Изменилась версия состояния либо занят lock | Дождаться другого запуска и повторить doctor; не удалять ветку состояния |
| `config_invalid` | Конфигурация неверна или не хватает обязательных настроек | Выполнить validate и сверить настройки и Secrets с руководством |
| `mutation_limit` | Слишком много изменений за запуск | Проверить план и `max_mutations`; повышать лимит только для проверенного плана |
| `change_ratio_limit` | Меняется слишком большая доля управляемых записей | Проверить план и `max_change_ratio`; подтвердить реальную смену адресов |
| `record_limit` | Превышен предел управляемых записей | Сократить наборы доменов; жёсткий предел — 100 |
| `plan_conflict` | Конфликт записей или владения | Разобрать подробный план; не удалять чужие записи и ownership |
| `recovery_required` | Предыдущая операция не завершена или её результат не подтверждён | Разобрать журнал и выполнить процедуру восстановления до нового обновления |
| `safety_blocked` | Не выполнено защитное условие команды | Проверить параметры и подробный отчёт; не отключать защиту ради зелёного статуса |
| `encryption_setup_invalid` | Не удалось подготовить защищённый отчёт | Проверить ключ шифрования и контекст Actions; сохранить исходный ключ состояния |
| `encryption_report_failed` | Не удалось безопасно зашифровать отчёт | Проверить шифрование и журнал до следующего apply; открытый подробный отчёт не публикуется |
| `interrupted` | Команда прервана | Повторить read-only проверку; при разрешённых записях сначала проверить журнал |
| `controller_error` | Причина не может быть безопасно классифицирована | Прочитать зашифрованный отчёт на доверенном устройстве и следовать runbook |

Несколько причин могут появиться одновременно: например, недоступный источник и отсутствие обязательного маршрута. Неизвестные сообщения не публикуются и не классифицируются по словам из внешнего ответа. Если ошибка возникла до подготовки шифрования, подробного artifact может не быть: начните с безопасного следующего шага в Summary.

Эти пояснения не меняют коды завершения и критерии успешного deployment. Подтверждённый sync с допустимыми необязательными предупреждениями остаётся успешным; конфликт, неподтверждённые DNS-ответы или незавершённые операции остаются ошибкой.

## Если сайт не открывается при зелёном статусе

Запись в журнале DNS подтверждает, что устройство запросило адрес. Она не подтверждает успешное HTTPS-соединение, вход или отправку сообщения. Страница состояния relay может проверять его DNS-сервер или другой сетевой маршрут; это не доказывает, что каждый нужный сайт доступен из вашей сети.

1. Запишите время, длительность и точную ошибку браузера. Проверьте, работают ли обычные сайты.
2. Сравните Wi-Fi и мобильный интернет с тем же DNS-профилем. Два устройства в одном Wi-Fi используют общий сетевой маршрут.
3. Запустите **doctor** с `apply=false` и `bootstrap=false` в Actions. Сравните Summary с последним запуском по расписанию. Не сбрасывайте состояние и не повышайте лимиты ради зелёного статуса.
4. Посмотрите зашифрованные результаты проверок: сравните опубликованный relay с другими кандидатами, включая время, статус TLS и причину отказа. Сам по себе тайм-аут не позволяет отличить перегрузку сервера от сетевой проблемы.
5. Если DNS и TLS проходят проверки, а сайт всё равно не работает, проверьте его в браузере. Успешный TLS подтверждает соединение и сертификат, но не работу приложения. Автоматический HTTP-запрос может получить проверку Cloudflare даже при работающем браузере.

Расписание раз в шесть часов — периодическое обслуживание, а не непрерывное обнаружение сбоев. Короткий сбой может начаться и закончиться между запусками. Повторная TLS-проверка после паузы уменьшает ненужные замены адресов при кратком отказе; она не предотвращает сбои relay. Замена большинства записей за один раз также может быть остановлена защитными лимитами и требует проверенного плана. Для постоянного уменьшения этой зависимости нужны независимые relay и отдельно проверенное переключение между ними.
