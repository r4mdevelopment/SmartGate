# Обновление настроенного форка

В форке хранятся код проекта и ваши настройки. При обновлении необходимо сохранить DNS-профиль, включённые сервисы, Secrets, ключ шифрования и ветку `smartgate-state`.

## Перед обновлением

1. Прочитайте [changelog](../../../CHANGELOG.md) и описание нужного релиза. Выберите тег либо проверенный коммит upstream; зелёная плашка сама по себе не подтверждает совместимость с вашими настройками.
2. В окружении `smartgate` своего форка временно установите `SMARTGATE_APPLY_ENABLED=false`. Запуски по расписанию могут продолжать проверки без записей.
3. Дождитесь завершения текущего sync или recovery. Отключение будущего apply не останавливает уже работающую команду. Если есть pending journal, восстановите его текущей версией до обновления.
4. Сохраните приватную копию TOML-конфигурации, каталога сервисов, текущего зашифрованного файла состояния и ключа шифрования. Запишите текущий коммит кода. Не сохраняйте Secrets или расшифрованное состояние в Git.

Не удаляйте ветку состояния, не создавайте новый ledger для существующего профиля и не повторяйте bootstrap. Зашифрованная копия привязана к исходному репозиторию и DNS-назначению; перенос её в другой форк не является миграцией.

## Обновление через GitHub

1. Создайте Pull Request между `main` своего форка и выбранной версией upstream через **Compare across forks**. Просмотрите изменения кода, workflow и конфигурации до слияния.
2. Сохраните свои значения в `config/smartgate.actions.toml`, `config/services.toml` и manifest своего relay. При конфликте конфигураций изучите обе версии. Не используйте **Discard commits**, чтобы стереть свои настройки.
3. Дождитесь успешного CI и изучите необходимые миграции, затем слейте PR в основную ветку своего форка. Не сливайте upstream в `smartgate-state`.
4. Сохраните Secrets и Variables окружения, если релиз явно не требует проверенной миграции. Ключ шифрования существующего состояния должен остаться прежним.

Если **Sync fork** предлагает чистое слияние, его можно использовать после просмотра сравнения. При конфликте создайте PR и разберите различия; не перезаписывайте свою конфигурацию принудительным обновлением.

## Проверка новой версии

В основной ветке откройте **Actions → SmartGate sync**:

1. Выполните `command=preview`, `apply=false`, `bootstrap=false`. Проверьте план и сообщения Summary.
2. Выполните `command=doctor` без apply и bootstrap. Проверьте DNS-ответы, обязательные маршруты и журнал. TLS-проверка в Actions не заменяет проверку сервиса на устройстве.
3. При нулевом плане и закрытом журнале можно выполнить `command=sync`, `apply=true`, `require_no_change=true`, `bootstrap=false`. Режим остановится при любых свежих DNS-операциях или pending recovery; служебные наблюдения состояния могут сохраняться.
4. После проверки совместимости верните `SMARTGATE_APPLY_ENABLED=true`, если раньше пользовались автоматическим обновлением.

Ненулевой план необходимо отдельно изучить перед обычным sync. Не повышайте лимиты только ради успешного статуса обновления. Если будущий релиз требует миграции состояния, выполняйте его инструкцию; bootstrap не является миграцией.

## Если обновление не удалось

Оставьте автоматическое применение выключенным и начните со [справочника причин](diagnostics.md) и [runbook](runbook.md). При pending journal сначала восстановите сохранённую операцию.

Откат коммита кода не отменяет DNS-изменения или миграцию формата состояния. Возвращайтесь к прежнему коду только если он совместим с текущим состоянием и конфигурацией. DNS rollback — отдельная команда для точного последнего журнала; восстановление старого зашифрованного файла поверх нового состояния может потерять ownership и не подходит для быстрого обхода ошибки.
