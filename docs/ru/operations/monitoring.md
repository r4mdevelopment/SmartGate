# Мониторинг маршрутов

**SmartGate monitor** сохраняет короткие DNS-, TLS- и HTTP-наблюдения опубликованных маршрутов. Он не меняет DNS-записи, не выбирает запасные адреса, не запускает recovery и не сохраняет состояние. Обычная синхронизация раз в шесть часов работает отдельно.

## Включение мониторинга

1. Завершите обычную настройку: зашифрованное состояние и успешная синхронизация уже должны быть готовы. Мониторинг использует существующие Secrets Environment `smartgate` и настройки DNS-адаптера.
2. Откройте **Actions → SmartGate monitor → Run workflow** на основной ветке. Посмотрите Summary; при необходимости скачайте зашифрованный artifact.
3. В **Settings → Secrets and variables → Actions → Variables** создайте **переменную репозитория** `SMARTGATE_MONITOR_ENABLED` со значением `true`.

Проверки запланированы на **11-ю и 41-ю минуту каждого часа**, по UTC. Для паузы установите переменную репозитория в `false`. Ручные проверки останутся доступны. В новых форках расписание мониторинга выключено до явного включения.

У job только `contents: read`; Environment подключён с `deployment: false`. Поэтому доступны существующие Secrets, а новый Deployment не создаётся. Job не может отправлять коммиты в ветку состояния. Дополнительный токен или ключ не нужен. Environment с custom deployment protection rules несовместим с этим режимом; перед включением нужна поддерживаемая конфигурация Environment. [Документация GitHub](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/deploy-to-environment).

## Что проверяется

Мониторинг читает зашифрованное состояние schema 2 и DNS API. Проверяются только совпадающие управляемые записи, максимум 100. Нужны правильная привязка DNS-профиля и завершённый журнал. Чужие DNS-записи не проверяются.

Для каждого маршрута запрашивается **A**-ответ настроенного DoH endpoint и выполняется анонимный **GET /** через сохранённый числовой IPv4. TLS проверяет сертификат исходного домена через SNI. Проверка не переходит по редиректам, не отправляет авторизацию или cookies, не сохраняет тела ответов и произвольные заголовки.

Одновременно выполняется максимум восемь проверок маршрутов. HTTP ограничен общим сроком в четыре секунды и заголовками в 16 KiB, включая максимум четыре промежуточных ответа. DoH использует ограниченные таймауты фаз транспорта и проверяет время после заголовков и каждого фрагмента тела; переходы между фазами могут увеличить общую длительность запроса сверх четырёх секунд. После истечения 30-секундного бюджета сбора новые проверки не начинаются; уже запущенные фазы транспорта могут закончиться позже. Непроверенные маршруты явно отмечаются. Подготовка и повторное чтение находятся вне этого бюджета; timeout job в Actions — три минуты.

После наблюдений API и состояние читаются повторно. Изменение во время проверки даёт `incomplete` с `snapshot_changed`: повторите после завершения sync. У мониторинга отдельная concurrency group; он не отменяет ожидающую синхронизацию.

## Как читать результат

| Результат | Значение |
| --- | --- |
| `observed` | Все маршруты вернули ожидаемый A-ответ и HTTP 2xx/3xx |
| `observed_with_warnings` | Сбор завершён; есть несовпадения DNS, ошибки TLS или HTTP-предупреждения |
| `incomplete` | Не все маршруты проверены, снимок изменился или сбор завершился ошибкой |

HTTP-наблюдения различают `response`, `challenge`, `authorization_required`, `http_rejected`, `rate_limited`, `server_error`, ошибки соединения/сертификата и некорректные ответы. Проверка Cloudflare и HTTP 403 не запускают смену адреса.

Успешный job означает, что наблюдения собраны; **он не подтверждает вход в браузере или работу приложения**. Ошибки проверяемых endpoint остаются видны как предупреждения. Ошибки настройки, владения записями или шифрования приводят к неуспешному job. Мониторинг не использует порог доступности sync в 85% и не создаёт Deployments.

Summary и `monitor.json` содержат только агрегаты. В `monitor.enc.json` находятся домены, адреса, результаты DNS, HTTP-статус, классификация, время и длительность проверки. Artifacts хранятся **семь дней**. История посещений устройств не собирается.

Для расшифровки используйте существующую [команду report-decrypt](privacy.md#чтение-подробного-отчёта), подставив имя `monitor.enc.json` и ID/attempt запуска мониторинга. Используется текущий ключ шифрования состояния и привязка к репозиторию/запуску. Не публикуйте расшифрованный отчёт без проверки содержимого.

## Частота и расход ресурсов

За 30 дней расписание раз в полчаса создаёт примерно **1 440 запусков**. Если каждый оплачивается как одна минута, только мониторинг использует около 1 440 минут; если как две — около 2 880, дополнительно к sync и CI. Это оценка, а не гарантия длительности. После первых запусков проверьте расход аккаунта; при необходимости выключите мониторинг или увеличьте интервал cron.

В приватных репозиториях используются общие минуты Actions и хранилище artifacts владельца. В публичных репозиториях вычисления на стандартных hosted runners бесплатны; правила хранения продолжают действовать. [Тарификация GitHub](https://docs.github.com/en/billing/concepts/product-billing/github-actions).

Для 25 маршрутов мониторинг также делает до **1 200 DNS-запросов в день**, дополнительно к sync и запросам устройств. HTTP-проверки создают дополнительный трафик relay. Частоту можно снизить, если такой расход не подходит.

GitHub может задерживать или пропускать scheduled jobs. Короткий сбой может попасть между проверками. Наблюдения выполняются с GitHub runner, а не из сети пользователя, и не восстанавливают сведения о сбое до включения мониторинга. [Ограничения расписания](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
