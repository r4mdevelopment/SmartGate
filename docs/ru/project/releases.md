# Подготовка релиза

Версия SmartGate хранится в `pyproject.toml`, а изменения для пользователей — в корневом [CHANGELOG.md](../../../CHANGELOG.md). Теги имеют формат `vMAJOR.MINOR.PATCH`. Релиз публикуется после проверки описания и артефактов.

## Подготовка черновика

1. В рабочей ветке обновите версию пакета и добавьте одну соответствующую запись changelog. Опишите поведение, обновление и ограничения. Выполните проверки из [руководства разработчика](../development/README.md).
2. Слейте проверенные изменения после успешного CI. Откройте **Actions → Prepare release → Run workflow** в основной ветке и введите точную версию без `v`, например `0.1.0`.
3. Workflow отклоняет неверную или несовпадающую версию, отсутствующие/пустые/повторные записи changelog, неуспешные тесты и сломанные ссылки. Затем собирает wheel и исходный архив, создаёт тег на коммите запуска и черновик релиза с обоими артефактами.
4. Проверьте тег, коммит, описание и артефакты черновика, затем опубликуйте релиз на странице GitHub.

Workflow запускается только вручную из основной ветки. Он не читает окружение `smartgate`, не использует DNS-ключи, не меняет DNS и не выполняет миграцию состояния. Тег или push не публикуют релиз автоматически. Подготовка черновика создаёт тег, поэтому перед запуском необходимо проверить коммит.

## Существующие теги и прерванная подготовка

Создание тега отклоняет уже существующий тег; workflow его не переносит и не перезаписывает. Если подготовка остановилась после создания тега, проверьте его точный коммит. Продолжите создание черновика вручную с подтверждённым тегом и артефактами либо выберите новую версию для новых изменений. Не удаляйте и не переносите опубликованные теги ради повторного запуска.

Первый релиз описывает весь MVP. Последующие записи changelog описывают изменения относительно последней опубликованной версии и необходимые миграции. Черновик — подготовка, а не подтверждение опубликованного релиза.
